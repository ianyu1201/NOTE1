# NOTE1 AI 协作开发流程与 V0.3 交付方案

> 状态：V0.3 任务编写、开发和验收规范  
> 更新日期：2026-08-03

## 1. 目标

解决长对话与多会话协作中的三个实际问题：

1. 已确认产品信息在交接中丢失；
2. 开发者依据模糊描述自行补全 UI；
3. 实现者用构建通过或单张截图代替完整验收。

核心方法不是增加更多对话，而是建立可追溯的任务合同：固定基线、固定范围、明确参考图、明确非回归能力、独立验收。

## 2. 角色与责任

角色是责任分离，不要求永久维护三个独立会话。

### 2.1 产品与设计责任

- 维护产品基线和术语；
- 明确问题、用户结果、范围和确认图；
- 区分已确认、假设和开放问题；
- 决定是否接受视觉或交互方案；
- 不凭空替开发者决定工程实现。

### 2.2 实现责任

- 只在任务允许范围内修改；
- 开工前阅读任务列出的全部基线；
- 先复现与记录现状，再改动；
- 保护 V0.1/V0.2 非回归能力；
- 提交自动验证和真实运行证据；
- 不以技术便利改变产品结构。

### 2.3 独立验收责任

- 在固定提交上独立运行验证；
- 对照验收项和确认图，而不是对照实现者描述；
- 检查功能、视觉、手势、无障碍和数据结果；
- 记录未覆盖项，不把“无法验证”写成“已通过”。

高风险任务的实现者与最终验收者必须不同；普通小任务可以由同一主任务协调，但仍需独立复核步骤。

## 3. 信息源与冲突处理

每个任务必须列出且按顺序读取：

1. 适用版本 PRD；
2. 产品设计与交互规格；
3. 非回归矩阵；
4. 当前 ISSUE；
5. 开发准则和 UI 完备性清单；
6. 当前代码、测试和固定提交；
7. 本任务专属确认图与状态图。

冲突时：

- 用户最新明确确认高于旧候选方案；
- 现役基线高于外部参考；
- 产品文档定义“做什么”，设计规格定义“长什么样、如何动”，开发文档不能反向改需求；
- 代码只代表当前实现，不自动成为产品要求；
- 无法判断时停止对应改动并记录冲突，不自行选择更方便的方案。

## 4. 开发前门禁

### 4.1 产品门禁

- [ ] 用户结果、范围内和范围外已明确。
- [ ] 术语使用项目标准名称。
- [ ] 未确认内容标记为假设或开放问题。

### 4.2 设计门禁

- [ ] 涉及页面已有确认图或可运行原型。
- [ ] 默认、空、内容、编辑、错误和键盘等适用状态完整。
- [ ] 手势有起始、进行中、阈值、成功、失败、取消和撤回说明。
- [ ] 参考图注明借鉴点和不可照搬部分。

### 4.3 工程门禁

- [ ] 固定完整 Git SHA。
- [ ] 工作树干净或已记录全部既有改动归属。
- [ ] 允许修改的目录和文件明确。
- [ ] 相关测试在改动前可运行。
- [ ] 数据迁移、附件和兼容性影响已评估。

任一门禁不满足时，可以补文档、做原型或诊断，但不能直接宣称进入正式开发。

## 5. 任务粒度

任务以“可独立验收的垂直切片”为单位，不以固定小时数作为硬规则。

合格示例：

- 卡片左滑收起：手势判定、反馈、数据状态、撤回和测试；
- 构思集归入：长按、拓展目标、列表选择、容量失败和状态保持；
- 小票册单张浏览：堆叠切换、下拉抽取、详情返回和减少动态效果；
- 附件唯一标识：迁移、同名用例、预览和删除回归。

不合格示例：

- “把 V0.3 UI 全部优化好”；
- “按参考图重做一下”；
- 同一任务同时修改导航、数据模型、备份、附件和小票动效。

## 6. 每个任务的固定合同

### 6.1 基本信息

- 任务名称和唯一编号；
- 唯一目标；
- 用户可观察到的结果；
- 固定基线提交；
- 前置文档与参考图；
- 允许修改范围；
- 禁止修改范围；
- 依赖和风险。

### 6.2 验收条件

每条验收条件必须可观察、可操作或可测量，并包含：

- 功能结果；
- 页面和视觉状态；
- 手势和动效；
- 数据持久化；
- 失败和边界状态；
- 无障碍和系统降级；
- 非回归项。

“看起来不错”“与设计一致”“测试一下”不是有效验收条件。

### 6.3 验证矩阵

| 层级 | 最低要求 |
| --- | --- |
| 静态检查 | 编译、警告、格式或相关规则 |
| 单元/领域测试 | 业务状态与边界 |
| UI/集成测试 | 关键入口和结果 |
| 模拟器 | 指定设备与系统的完整步骤 |
| 真机 | 手势、键盘、权限、附件、分享、VoiceOver |
| 视觉证据 | 与指定确认图同状态、同设备比例对照 |

任务只报告实际完成的层级。模拟器通过不得写成真机通过。

## 7. 推荐工作流

### 阶段 A：固定基线

1. 记录提交、分支、工作树状态；
2. 运行改动前测试；
3. 保存涉及页面的现状证据；
4. 核对 ISSUE 与非回归矩阵。

### 阶段 B：最小实现

1. 只修改任务允许范围；
2. 先实现状态和数据，再接视觉细节；
3. 使用集中设计变量和既有组件；
4. 保留失败回滚和兼容路径。

### 阶段 C：开发者自验

1. 运行相关测试和完整构建；
2. 在指定模拟器完成任务步骤；
3. 检查默认、边界、键盘和错误状态；
4. 输出修改摘要、验证结果和未覆盖项。

### 阶段 D：独立验收

1. 验收者切到同一固定提交；
2. 重新运行关键验证；
3. 对照确认图和交互状态图；
4. 对照非回归矩阵；
5. 将问题写入 ISSUE，标明证据和严重级别。

### 阶段 E：封存

1. 关闭 ISSUE 或记录明确豁免；
2. 生成证据索引；
3. 固定提交或版本标记；
4. 更新交接文档，不用聊天摘要代替仓库事实。

## 8. V0.3 推荐分段

### 8.1 V0.2.1 稳定化

- 附件身份；
- 备份恢复线程与失败回滚；
- 复核 ADR-004 的单一活跃代码路径与非回归映射；
- 性能测量；
- 真机和无障碍证据。

### 8.2 V0.3 设计冻结

- 四页总览；
- 核心交互状态图；
- 视觉变量和组件状态；
- 参考图验收映射；
- 试用脚本。

### 8.3 V0.3 垂直切片开发

建议顺序：

1. 全局页面框架、顶部栏、底部导航、浮动按钮和设计变量；
2. 灵感页与录入面板；
3. 卡片预览与归入构思集；
4. 构思集总页与工作台；
5. 结束本轮与小票生成；
6. 小票册、详情、导出和分享；
7. 搜索、选择、回收站、设置与全局无障碍收口。

每一步必须保持主分支可构建、相关闭环可运行。

## 9. 变更控制

- 开发中出现新想法，默认进入待讨论或后续版本，不自动扩大当前任务。
- 若新信息证明当前任务产品定义错误，应暂停对应实现、更新基线并重新冻结，而不是机械完成错误方案。
- 任何删除、重命名、数据迁移或产品范围变化必须单独说明影响并获得授权。
- 外部开源项目和 Skill 只能提供实现与审美参考，不能覆盖 NOTE1 已确认设计。

## 11. 统一完成定义

任务只有在以下条件满足时才可标记完成：

- 代码或文档达到任务唯一目标；
- 验收条件逐条有结果；
- 相关自动验证通过；
- 需要的运行证据已保存；
- 非回归项已检查；
- 未覆盖项明确披露；
- 独立验收没有未关闭的阻断问题；
- 仓库中的基线、ISSUE 和证据索引已更新。

“已经写完”“构建成功”“看过模拟器”“和截图差不多”都不足以单独构成完成。
